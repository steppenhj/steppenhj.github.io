Why WebSocket?

Context: 웹 브라우저(Client) 파이썬 서버

  • Reason: 브라우저 보안 제약으로 Raw UDP 사용이 불가합니다. HTTP 오버헤드를 줄이고 연결을 유지(Keep-alive)하기 위해 WebSocket을 선택했습니다.
  • Note: UI의 Latency는 Network Round-Trip Time (RTT)을 의미합니다.

Why UDP?

Context: 파이썬 게이트웨이 C++ 엔진

  • Reason: 제어 데이터는 "과거의 확실함(TCP)"보다 "손실되더라도 현재의 데이터(UDP)"가 중요합니다. Head-of-Line Blocking을 방지했습니다.

C++: Hardware Watchdog

UDP 소켓 옵션을 활용하여 통신 두절을 감지하고, 비상시 즉시 액추에이터를 정지합니다.

drive_server.cpp (Fail-safe)
// Safety Layer 3: 500ms Timeout Watchdog
struct timeval tv = {0, 500000}; 
setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO, ...);

while (true) {
    int n = recvfrom(sock, &data, ...);
    // 타임아웃 발생 시 즉시 정지
    if (n < 0) motors.stopAll(); 
    else motors.setSpeed(data.th);
}

Engineering Insight: OS Limitation

Python 대신 C++로 하드웨어 제어기를 작성하여 연산 효율을 높였지만, 범용 OS(General Purpose OS)인 리눅스의 스케줄링 한계는 여전히 존재했습니다.

⚠️ Kernel Preemption Jitter

  • Issue: C++ 프로세스가 빨라도, 리눅스 커널이 백그라운드 작업(Wi-Fi 등)을 위해 CPU를 선점하면 수십 ms의 지연이 발생합니다.
  • Result: "완벽한 정시성(Hard Real-time)을 위해서는 MCU(STM32)가 필수적이다."

Solution: Offload Control to STM32
Proceed to Phase 2

Baseline Findings → Requirements

  • Issue: Linux 환경에서 제어 루프가 부하/스케줄링 영향으로 지연 변동(jitter)이 발생
  • Risk: 폐루프 제어의 예측 가능성 저하 → 불안정/안전 리스크
  • Requirement: 액추에이션은 Hard real-time 도메인(MCU)으로 분리 필요
  • Carried Over: 통신 두절 시 Timeout Watchdog 및 단계적 안전정지 원칙 유지
