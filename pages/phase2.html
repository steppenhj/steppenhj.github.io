Why Split the System?

Context: 단일 프로세서(RPi)의 OS 스케줄링 간섭으로 인한 제어 불안정.

  • Architecture: "Brain(RPi) - Reflex(STM32)" 구조.
  • Role - RPi: OpenCV 영상 처리 및 WebSocket 서버 (Non-Realtime).
  • Role - STM32: 모터 PWM 생성(Hard Real-time).

Communication Interface

Context: 디버깅 용이성과 개발 속도를 고려한 ASCII Protocol 채택

Protocol: ASCII CSV

복잡한 바이너리 패킷 대신 가독성(Human-readable)이 높은 CSV 포맷을 사용하여 시리얼 터미널에서 즉각적인 디버깅이 가능하도록 설계했습니다.

Payload: "THROTTLE,STEERING\n" (ex: "100,1500\n")
Implementation: Polling & Parsing

초기 단계의 안정성을 위해 Polling 방식으로 수신하며, sscanf를 통해 정수형 데이터를 추출합니다. 

// main.c: Simple ASCII Parsing
if (rx_data == '\n') {
    buffer[idx] = 0; // Null Terminate
    sscanf((char*)buffer, "%d,%d", &speed, &angle);
}

Hardware Utilization

소프트웨어의 개입을 최소화하기 위해 STM32의 내부 타이머(TIM) 하드웨어를 적극 활용했습니다.

Encoder: Hardware Counter

Mechanism: TIM1을 Encoder Interface Mode로 설정.

  • GPIO 인터럽트 방식이 아님
  • CPU가 코드를 실행하지 않아도 하드웨어 레지스터가 펄스를 자동 카운팅
  • 고속 주행 시에도 CPU 부하(Overhead) Zero

Safety: Multi-Layer Logic

Software Lock (Py): eventlet.semaphore로 시리얼 자원 충돌 방지.
Hardware Failsafe (C): 통신 두절 시 자동 정지 로직 구현.

if (HAL_GetTick() - last_cmd > 500) Stop();

→ 이후 개선 사항은 Phase 03에서 구현됩니다.

이에 화려한 최신 기술보다 '완전한 통제'를 최우선 목표로 삼았습니다. 불확실성을 줄이기 위해 Polling과 ASCII 프로토콜로 디버깅 가능한 환경을 먼저 구축했고, 대신 리얼타임 성능은 하드웨어 타이머에 전적으로 위임하는 실용적인 접근을 택했습니다."
