Baseline: UART 기반 End-to-End RTT

CAN 전환 전, 기존 UART 아키텍처의 전체 왕복 응답 시간을 Ping-Pong Echo 방식으로 측정하여 기준선을 확보했습니다.

40.1 ms

End-to-End Round-Trip Time (20회 평균)

Browser(JS) → WiFi → Python → UDP → C++ → UART 115200bps → STM32 → 역방향 복귀

PING 버튼으로 20회 연속 측정, 평균 RTT 40.1ms 확인

측정 방법: STM32 펌웨어 ISR에서 "PING" 수신 시 즉시 "PONG"을 반환하는 에코 방식. 이 수치에는 WiFi 왕복(~10ms), WebSocket 오버헤드(~5ms), UDP 로컬(<1ms), UART 전송(~1-2ms), 각 계층의 태스크 스케줄링 지연이 모두 포함되어 있습니다.

전환 동기: UART 단일 채널의 구조적 한계

  • 모터 명령(TX)과 엔코더 피드백(RX)이 동일 UART를 공유 → Blocking 전송 시 수신 인터럽트 밀림 가능
  • ECU 추가 시 UART 채널을 물리적으로 추가해야 하는 확장성 한계
  • 에러 감지 및 재전송 메커니즘이 프로토콜 레벨에서 부재 — 애플리케이션에서 직접 구현 필요

UART vs CAN 비교

관점 UART (Phase 5) CAN (Phase 6)
토폴로지 1:1 Point-to-Point N:N 멀티노드 버스
ECU 확장 UART 채널 추가 필요 버스에 노드 연결만으로 확장
우선순위 소프트웨어 레벨 구현 Message ID 기반 HW 아비트레이션
에러 처리 없음 (앱 책임) CRC, ACK, 자동 재전송 내장
속도 115200 bps 500 kbps (약 4.3배)

CAN Message ID 설계 설계 예정

CAN 버스에서 Message ID가 곧 우선순위입니다. ID 값이 낮을수록 아비트레이션에서 우선권을 가지므로, 안전 관련 메시지에 낮은 ID를 할당합니다.

ID (Hex) 방향 내용 주기
0x010 Sensor → All 비상 정지 (장애물 임박) 이벤트
0x100 RPi → Motor ECU 속도 + 조향 명령 20ms
0x200 Motor ECU → RPi 엔코더 피드백 50ms
0x300 Sensor ECU → RPi 초음파 거리 데이터 100ms
0x7F0 RPi → All Ping (RTT 측정) 요청 시

박해진's Note

"Phase 5까지의 UART 아키텍처는 단일 ECU 구성에서 잘 동작했지만, 센서 노드를 추가하려는 순간 구조적 한계에 부딪혔습니다.

CAN 전환은 속도 개선이 아니라, 멀티 ECU 확장성과 프로토콜 레벨의 에러 핸들링을 확보하기 위한 아키텍처 결정입니다. bxCAN(하드웨어 CAN)과 MCP2515(SPI-CAN)을 동일 버스에서 운용하면서, SPI 통신과 CAN 프로토콜 두 가지를 동시에 경험할 수 있었습니다."
