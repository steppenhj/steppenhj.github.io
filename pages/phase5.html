PHASE 05: RTOS MIGRATION

Real-Time Operating System

시스템의 복잡도가 증가함에 따라, 슈퍼 루프(Super Loop) 구조의 한계를 넘기 위해
FreeRTOS를 도입하여 태스크 기반의 선점형 멀티태스킹 환경을 구축했습니다.

Why RTOS?

Phase 4까지 기능이 확장되면서 단일 루프에서 센서 수신, 모터 제어, 안전 감시, 통신 파싱을 모두 처리하기 어려워졌습니다. 특정 작업(예: 긴급 정지)이 다른 작업(예: 로그 출력)에 의해 지연되지 않도록 우선순위(Priority) 관리가 필수적이었습니다.

  • BEFORE (Super Loop)
    순차 실행. 앞선 함수가 늦어지면 전체 시스템 Latency 증가 (Jitter 발생).
  • AFTER (RTOS)
    높은 우선순위 태스크(Motor Control)가 CPU를 선점(Preemption). 정시성 보장.

Task Architecture

기능별로 스레드(Thread)를 분리하고 중요도에 따라 우선순위를 차등 배분했습니다.

Task Name Priority Period Role
Safety_Task Realtime (High) 5ms Emergency Stop & Heartbeat Check
Motor_Control High 10ms PID Calculation & PWM Update
Comm_Task Normal Event UART Packet Parsing (DMA)
Logger_Task Low 500ms System State Logging

IPC: Message Queue

전역 변수 사용을 지양하고, 태스크 간 데이터 전달을 위해 Queue를 사용했습니다. 이를 통해 Race Condition을 원천 차단했습니다.

stm32_main.c
// 1. Communication Task (Producer)
void StartCommTask(void *argument) {
  while(1) {
    if (UART_NewData) {
        // Put data into Queue (Wait 0ms)
        osMessageQueuePut(CommandQueue, &cmd_data, 0, 0);
    }
    osDelay(10);
  }
}

// 2. Motor Task (Consumer)
void StartMotorTask(void *argument) {
  Command_t recv_cmd;
  while(1) {
    // Block until data arrives (Max 10ms)
    if (osMessageQueueGet(CommandQueue, &recv_cmd, 0, 10) == osOK) {
        Update_PID(recv_cmd);
    }
  }
}

Debugging: Stack Overflow

RTOS 도입 초기, 시스템이 불규칙적으로 Hard Fault에 빠지는 현상이 발생했습니다.

  • Cause: `printf` 함수가 내부적으로 많은 스택 메모리를 사용하여 Comm_Task의 스택(128 Words)이 넘침.
  • Detection: vApplicationStackOverflowHook() 함수를 활성화하여 감지.
  • Solution: Task Stack Size를 256 Words로 증설하고, 경량화된 로깅 함수로 교체.

박해진's Note

"RTOS를 도입하면서 '언제 실행되는가'에 대한 제어권을 OS에게 위임하는 사고의 전환이 필요했습니다. Context Switching 오버헤드를 고려하더라도, 시스템의 확장성(Scalability)과 유지보수성 측면에서 필수적인 선택이었습니다."
