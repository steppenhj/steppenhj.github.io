Why OTA? — The Problem

펌웨어를 수정할 때마다 차량의 케이스를 분해하고, ST-Link를 물리적으로 연결해야 했습니다.
실제 자동차 ECU도 동일한 문제를 갖고 있으며, 이를 해결하는 기술이 IAP(In-Application Programming)입니다.

BEFORE (ST-Link)

① 코드 수정 → CubeIDE 빌드
② 케이스 분해
③ UART 선 분리 (RPi 연결 해제)
④ ST-Link USB 연결
⑤ Flash Download
⑥ ST-Link 분리 → 재조립
⑦ 테스트

AFTER (OTA)

① 코드 수정 → CubeIDE 빌드
② 브라우저에서 .bin 업로드
③ 자동 업데이트 완료
④ 테스트

물리적 접촉 불필요. RPi-STM32 연결 유지.

Flash Memory Layout (STM32F411RE)

512KB Flash를 두 영역으로 분할합니다. Sector 0에 부트로더가 상주하며, Sector 1~7에 애플리케이션(FreeRTOS 코드)이 위치합니다.

Implementation: Three Layers

Layer 1: Custom Bootloader (STM32)

CubeIDE에서 별도 프로젝트로 생성한 Bare-metal 부트로더입니다.
FreeRTOS 없이 최소한의 코드로 Flash 쓰기에만 집중합니다.

  • UART 대기: 부팅 후 3초간 "UPDATE\n" 문자열 수신 대기. Timeout 시 App 점프.
  • Flash Erase: HAL_FLASHEx_Erase()로 Sector 1~7 삭제. Sector 0(부트로더)은 절대 건드리지 않음.
  • Chunk Receive: 256바이트 단위로 UART 수신 → HAL_FLASH_Program()으로 Word(4B) 단위 기록.
  • CRC Verify: 소프트웨어 CRC32(다항식 0xEDB88320)로 Flash 영역 전체를 검증. Python의 zlib.crc32()와 동일한 결과를 비교.
  • Jump to App: Vector Table 재설정(SCB→VTOR) 후 Application Reset Handler로 점프.
bootloader_main.c
// 1. 업데이트 신호 대기 (3초 Timeout)
if (WaitForUpdateSignal(3000) == TIMEOUT) {
  JumpToApp(); // 신호 없으면 즉시 정상 부팅
}

// 2. Flash Erase (Sector 1~7만)
HAL_FLASH_Unlock();
FLASH_EraseInitTypeDef erase = {
  .TypeErase = FLASH_TYPEERASE_SECTORS,
  .Sector = FLASH_SECTOR_1,
  .NbSectors = 7
};
HAL_FLASHEx_Erase(&erase, &error);

// 3. 바이너리 수신 & 기록 (256B 청크)
while (received < total_size) {
  HAL_UART_Receive(&huart2, chunk, 256, 5000);
  for (int i = 0; i < 256; i += 4) {
    HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD,
      APP_ADDRESS + received + i,
      *(uint32_t*)&chunk[i]);
  }
  HAL_UART_Transmit(..., "ACK", ...);
}

// 4. CRC 검증 후 재부팅
if (VerifyCRC() == OK) NVIC_SystemReset();

Layer 2: Flasher Script (RPi)

RPi에서 실행되는 Python 스크립트로, 기존 app.py에 업데이트 엔드포인트를 추가합니다.
기존 제어 모드를 중단한 뒤 부트로더와 통신합니다.

  • Step 1 — 제어 모드 중단: C++ 프로세스 종료 → UART 점유 해제.
  • Step 2 — STM32 리셋: RPi GPIO로 STM32의 NRST 핀을 Low→High 토글하여 하드웨어 리셋.
  • Step 3 — Handshake: 리셋 직후 UART로 "UPDATE\n" 전송. "READY" 응답 대기.
  • Step 4 — Streaming: .bin 파일을 256바이트 청크로 분할 → 전송 → ACK 수신 → 다음 청크.
  • Step 5 — 완료: CRC 전송 → STM32 자동 재부팅 → C++ 프로세스 재시작.
ota_flasher.py
import serial, struct, zlib, os

def flash_firmware(bin_path):
  # 1. C++ 제어 프로세스 중단
  os.system("pkill control_core")

  # 2. STM32 하드웨어 리셋 (GPIO)
  reset_stm32() # NRST Low→High

  # 3. 부트로더 Handshake
  ser = serial.Serial('/dev/ttyACM0', 115200)
  ser.write(b'UPDATE\n')
  resp = ser.readline() # "READY\n"

  # 4. 바이너리 청크 전송
  data = open(bin_path, 'rb').read()
  ser.write(struct.pack('<I', len(data)))

  for i in range(0, len(data), 256):
    chunk = data[i:i+256].ljust(256, b'\xff')
    ser.write(chunk)
    ser.readline() # "ACK\n" 대기

  # 5. CRC 전송 & 완료
  crc = zlib.crc32(data) & 0xFFFFFFFF
  ser.write(struct.pack('<I', crc))

Application 수정사항

기존 FreeRTOS 애플리케이션도 한 줄 수정이 필요합니다.
시작 주소가 0x0800_0000이 아닌 0x0800_4000이므로 Vector Table 오프셋을 재설정해야 합니다.

system_stm32f4xx.c (수정)
// 기존 (0x0800_0000에서 직접 실행)
// #define VECT_TAB_OFFSET 0x00

// 변경 (부트로더 뒤에서 실행)
#define VECT_TAB_OFFSET 0x4000

UART Handshake Protocol

부트로더와 Python Flasher 간의 통신 프로토콜입니다. 모든 단계에서 ACK/NACK 확인을 통해 데이터 무결성을 보장합니다.

RPi (Python)                 STM32 (Bootloader)
   "UPDATE\n" ──────────→
                  ←────────── "READY\n"
   [4B: total_size] ──────────→
                  ←────────── "ACK\n"
   [256B: chunk 0] ──────────→
                  ←────────── "ACK\n"
   [256B: chunk 1] ──────────→
                  ←────────── "ACK\n"
          ...반복...
   [4B: CRC32] ──────────→
                  ←────────── "DONE\n" (→ 재부팅)

Safety: Fail-safe & Recovery

전송 중 통신 끊김

Problem: 청크 전송 도중 WiFi 끊김 → Flash가 불완전한 상태.
Solution: ACK 5초 Timeout 시 부트로더가 NVIC_SystemReset()으로 재부팅. 재전원 시 부트로더가 다시 시작되어 재시도 가능. 부트로더 자체는 Sector 0에 있어 절대 손상되지 않으므로 전원만 넣으면 재시도 가능.

CRC 불일치

Problem: 전송 완료 후 CRC가 맞지 않음 → 손상된 펌웨어 실행 위험.
Solution: CRC 불일치 시 "NACK" 전송 후 NVIC_SystemReset()으로 재부팅. 부트로더가 다시 3초 대기하므로 재전송 가능.

전원 차단 복구

Problem: Flash 쓰기 중 배터리 분리.
Solution: 부트로더(Sector 0)는 쓰기 대상이 아니므로 항상 살아있음. 재전원 시 부트로더가 정상 시작 → 업데이트 재시도 가능. "Bricking 불가" 구조.

박해진's Note

"처음에는 '부트로더'라는 개념이 막연했습니다. 하지만 구현하고 보니 원리는 단순합니다 — Flash 메모리를 둘로 나누고, 앞쪽의 작은 프로그램이 뒤쪽의 큰 프로그램을 교체하는 것.

핵심은 '부트로더 자체는 절대 덮어쓰지 않는다'는 설계 원칙입니다. 이 원칙 하나로 전송 실패, CRC 불일치, 전원 차단 등 모든 예외 상황에서 시스템이 복구 가능해집니다.

실제 자동차 ECU의 펌웨어 업데이트(UDS 프로토콜 기반)도 이 원리 위에 보안 인증과 암호화 계층이 추가된 것이라는 점에서, 이번 Phase는 전장 소프트웨어의 핵심 메커니즘을 직접 체득하는 경험이었습니다."
